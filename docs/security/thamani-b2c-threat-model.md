# Thamani B2C threat model

Gate 19 treats a Thamani consumer as a Principal isolated from every other consumer, from the ZuriBeans B2B Estate, and from their own past identity once anonymised. Client-supplied `customerId` claims are never authoritative on their own — every check below is a separate, server-side, fail-closed control.

| Threat                                                | Control                                                                                                                                                                  | Automated evidence                                         |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------- |
| Cross-customer IDOR                                   | A resource's `customerId` must equal the authenticated session's                                                                                                         | `thamani-customer-authorization.test.ts`                   |
| Guest-order-number enumeration                        | Guest order lookup requires the order's own email to match, not the order number alone (ADR-0017 §102); a wrong number and a wrong email produce the identical error     | `thamani-customer-authorization.test.ts`                   |
| Guest-order-lookup brute force                        | Lookup attempts are rate-limited per caller                                                                                                                              | `rate-limit.test.ts`                                       |
| Cross-Estate leakage (B2B membership on a B2C record) | A consumer record carrying `organisationId`/`membershipId` is rejected                                                                                                   | `thamani-customer-policy.test.ts`                          |
| PII leakage into canonical events                     | Personal-data keys are rejected from event payloads, independent of the credential check                                                                                 | `pii-guard.test.ts`, `verify:thamani-events`               |
| PII leakage into logs/analytics                       | The structured logger redacts personal-data keys, not just credentials; analytics projections carry no identifying field at all                                          | `observability.test.ts`, `thamani-customer-policy.test.ts` |
| Retained identity after a deletion request            | Anonymisation replaces every identifying field but keeps `customerId` stable for order/ERP referential integrity; refused while an order is open or a payment is pending | `thamani-customer-anonymisation.test.ts`                   |

The checks fail closed. A guest order lookup never reveals which half of the input was wrong (order number vs. email), so it cannot be used as an oracle to discover valid order numbers. Anonymisation is a irrecoverable identity replacement, not a hard delete — `customerId` must survive so existing orders and ERP projections keep a valid reference (ADR-0008 §127/§128, ADR-0017 §70). Logs and events contain references and correlation IDs, never raw email, phone, name, address or payment credentials.

See `docs/security/zuribeans-b2b-threat-model.md` for the ZuriBeans B2B Estate's equivalent threat model; `assertNoPersonalData` (`src/baobab/security/pii-guard.ts`) is shared by both.
