# Payments runbook

ADR-0015 §153's eleven required topics, each naming the control that already exists in code and the first action an operator takes. This repository owns the detection signal and the reference in each row; it does not own alert routing or paging (`docs/operations/observability.md`).

| Situation                       | Detection                                                                                                                                                                     | First action                                                                                                                                                                                                                                 |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Provider outage                 | `dependency_health` gauge `DOWN`/`DEGRADED` for the provider; `THAMANI_DASHBOARD`/`ZURIBEANS_DASHBOARD`'s `dependencyDown` alert                                              | Fail over to the Market's other configured provider if one exists; otherwise hold new payment intents and surface a checkout-level error rather than a silent retry loop.                                                                    |
| Unknown payment                 | A provider webhook or reference with no matching `CommercePayment` row                                                                                                        | Do not create a payment record from the webhook alone — resolve the order/reference through `PaymentBridgeRecordAdapter.findByIdempotencyKey` first; an unresolvable reference is a provider-side or integration bug, not customer error.    |
| Duplicate-charge suspicion      | Two `CommercePayment` rows for the same `orderReference`/`idempotencyKey`, or `MedusaPaymentOrchestrationAdapter.initiate`'s idempotent find-or-create returning a second row | Idempotency keys are supposed to make this impossible — treat a duplicate as a bug in the caller (a retry with a fresh key) rather than reconciling by hand first; confirm both rows' `idempotencyKey` before assuming a real double-charge. |
| Capture failure                 | Provider webhook reports capture failure; `transition` to `CAPTURED` rejected by the `TRANSITIONS` state machine (`orchestration-port.ts`)                                    | Leave the payment in its current state (never force a transition past the state machine) and re-drive capture through the provider once the underlying cause (funds, auth expiry) is resolved.                                               |
| Refund failure                  | Provider webhook reports refund failure after a `transition` to a refund-in-progress state                                                                                    | Same as capture failure — the state machine already refuses an invalid next state; investigate the provider-side reason before retrying.                                                                                                     |
| Webhook outage                  | No webhooks received for a provider within its expected interval                                                                                                              | Compare `CommercePayment` rows stuck `PENDING`/`AUTHORIZED` against the provider's own dashboard; a real outage needs a manual reconciliation pass once webhooks resume, not a bulk status guess.                                            |
| Webhook signature failure       | Signature verification rejects an inbound webhook                                                                                                                             | Treat as a security event, not a retry target — do not process the payload. Confirm the provider's signing secret hasn't rotated before assuming an attack.                                                                                  |
| ERP payment integration failure | `reconcilePaymentWithErp` returns `PENDING_ERP` (`ERP_MISSING`) past `RECONCILIATION_SLO_MINUTES.PAYMENTS` (30m); `paymentReconciliationSlaBreach` alert                      | Check the ERP integration adapter's own health before re-queuing — a stuck `PENDING_ERP` row usually means the projection never reached iDempiere, not that iDempiere disagrees with it.                                                     |
| Settlement mismatch             | `reconcilePaymentWithErp` returns `VARIANCE` with `AMOUNT_MISMATCH`/`CURRENCY_MISMATCH`/`STATUS_MISMATCH`                                                                     | Never auto-resolve a `VARIANCE` row — `amountDeltaMinor` and `reasons` tell you which side disagrees; escalate to whoever owns the ERP's financial record before writing back to either system.                                              |
| Merchant credential rotation    | Planned                                                                                                                                                                       | Rotate in the target provider's dashboard first, verify a test payment authorises, then update the deployment platform's secret store — never commit a credential to this repository.                                                        |
| Provider migration              | Planned                                                                                                                                                                       | Add the new provider as an additional configured provider for the Market first (do not remove the old one), let in-flight payments on the old provider finish naturally, then withdraw it once its `CommercePayment` backlog is empty.       |
